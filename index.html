Buying a €666 Halloween box for €0

The APIRoot causeDead endsImpactFix

Every visitor gets €66 of store credit. The limited edition box costs €666, so checkout only opens once the discount reaches 90.1%. Two public coupons exist: NIGHT20 (20%) and NEWS30 (30%), and the server refuses a coupon that is already applied.

That refusal only looks at the coupon applied last. Put another code in between and the first one works again. The cart on the right replays the real behavior, so try it yourself.

A small API with two numbers that matter

The client code in /static/js/app.js lists the whole surface. The session starts with 6600 cents of credit and the target item costs 66600 cents.

GET/api/sessioncreates the session, returns the credit
GET/api/products, /api/cartcatalogue, cart and totals
POST/api/cart/itemsadd a product
POST/api/cart/coupon, /removeapply or remove a promotion code
POST/api/checkoutplace the order
POST/api/newsletterreturns the NEWS30 welcome coupon for any valid email

Both coupons stack additively, but 50% off leaves €333, five times the credit. A repeated NEWS30 is rejected, yet each promotion in the response carries a count field and the UI renders count > 1 as "× count". That field only makes sense if repeats are a supported state, so the check had to be weaker than it looked.

The discount is exactly 2 × 30% + 2 × 20% of the subtotal. The arithmetic is impeccable. The policy is not.

The invariant that was never enforced

The rule should be "a coupon code appears at most once in the cart". The server enforces "the same coupon cannot be applied twice in a row", the coupon equivalent of checking only the last item on a shopping list. This is reconstructed from outside, but it matches every request observed.

What the server does

if code == session.last_coupon:
    return error("Coupon already applied.")
apply(code)          # count += 1
session.last_coupon = code

What it should do

code = normalize(code)
if code in session.coupons:
    return error("Coupon already applied.")
session.coupons.add(code)
apply(code)

What did not work

Ruling out the obvious bypasses first isolated the real issue. Open each one.

Direct duplicate

NEWS30 twice in a row is blocked, as intended.

Case, whitespace and Unicode lookalikes

Codes are normalized before the lookup, so a variant cannot create a second entry.

Race condition

20 parallel applications of one code gave one success and 19 "Coupon already applied". One winner, nineteen sore losers.

Mass assignment and negative quantity

Adding percent, amount, count, discount or price to the body changes nothing. The cart endpoint ignores quantity and always adds one unit.

More coupons

A small dictionary of seasonal names and numbers found no third code. Only NIGHT20 and NEWS30 exist.

The only lever was the order in which the two legitimate coupons are applied.

Impact

An unauthenticated visitor gets the most expensive item for free and keeps the €66 credit. On a real storefront the same logic applies to every product and every customer: free orders, inventory drain and repeatable fraud, with no account required. The exploit is deterministic, takes four requests and needs no race or victim interaction, so a rate limit would not help.

The challenge rules require Medium and the store holds no real customer data, so the submission stays Medium. The class is price manipulation through a business logic error.

Remediation

  • Reject a code that exists anywhere in the promotions list. Normalize it and keep applied codes in a set keyed by the normalized code.
  • Recompute the discount from the distinct promotions and cap the total at max(0, subtotal - discount) as defense in depth.
  • Make checkout recompute every amount from server-side cart state, never from client input (already the case here).
  • Add regression tests for repeated and alternating coupon sequences, and apply the same check to the removal path and any future stacking rule.

Takeaways

  • A duplicate check that only looks at the last element is not a duplicate check. When a response exposes a count, ask what state lets it exceed one.
  • Try interleaving, not just repeating. Many state bugs only appear when two values alternate.
  • Rule out the boring bypasses first. It makes the real bug obvious instead of speculative.
